# System architecture

epubtrans is a Bun-workspaces TypeScript monorepo. One engine (`@epubtrans/core`) is shared by a browser app and a CLI. There is no backend.

```
            +--------------------+       +------------------+
            |  apps/web          |       |  apps/cli        |
            |  React, IndexedDB  |       |  Bun binary      |
            |  DOM: browser      |       |  DOM: linkedom   |
            +---------+----------+       +---------+--------+
                      |      DomEnv, fetch, storage    |
                      +--------------+-----------------+
                                     v
                          +----------------------+
                          |  packages/core       |
                          |  import, segment,    |
                          |  translate, export,  |
                          |  project file        |
                          +----------+-----------+
                                     | HTTPS, key only to the chosen endpoint
                                     v
              Anthropic | OpenAI | Gemini | OpenRouter | DeepSeek | custom
```

## Core pipeline (`packages/core`)

1. **Import** (`import/import-book.ts`). `formats/detect-format.ts` recognizes EPUB, MOBI, AZW3 and FB2 from the bytes and file name. MOBI/AZW3 are converted by the vendored foliate-js parser (`third-party/foliate-js/mobi.js`, with an injected DOM), FB2 by an own converter. Everything is normalized into one in-memory EPUB package, so the later stages have a single path. DRM (MOBI encryption flag, EPUB `rights.xml` or non-font `encryption.xml`) is detected and rejected with a clear error.
2. **Segmentation** (`segment/segment-document.ts`). Block-level text in each content document is split into segments with ids `c{chapter}-{n}`; segment markers (`data-et-id`) are written into the normalized EPUB. Code, `pre`, math, SVG and similar blocks are skipped. The table of contents becomes chapter 0 (`TOC_CHAPTER_TITLE`) so TOC titles are translated too.
3. **Project** (`types.ts`). A `Project` holds settings, chapters with segments (`pending`, `translated`, `reviewed`, `error`) and the normalized `sourceEpub` bytes. `project/project-file.ts` saves it as a `.epubtrans` zip (`project.json` + `source.epub`) and validates untrusted state on load (`validateProjectState`, also used for IndexedDB rows).
4. **Translation** (`translate/`).
   - `translate-project.ts` translates every `pending` or `error` segment (that is what makes runs resumable), in batches of up to about 1500 source tokens, with a configurable number of parallel requests (1 to 16). With `twoPass`, a review pass follows over every `translated` segment.
   - Protocol (`prompt-protocol.ts`): system prompt = stable prefix (role, language pair, guideline) plus rules; the batch-relevant glossary travels in the user message (see below); user message = JSON `{"segments":[{"id","html"}]}`; the model must answer the same JSON shape.
   - `empty-element-markers.ts` keeps empty inline elements away from the model. Page markers such as `<a id="p49"></a>` or `<span epub:type="pagebreak" id="p12"></span>` hold no text, so a model restructuring the sentence drops them and the segment would fail validation every time. Before a batch is sent (translate pass, review pass for both source and draft, `retranslateSegment`, samples), every non-void element without any child node is detached together with the share of source text characters before it. After the reduced answer validates, the elements are put back at the same text fraction, snapped to the nearest word start (any character for CJK/Thai-like text without spaces), never inside a tag or inside an element of the same name, in original order, with 0 and 1 meaning start and end. A review reuses the draft's marker positions when the draft carries the same markers. The restored HTML is validated again against the full source, so stored translations keep the ids that TOC and index links point to. Void elements (`br`, `img`) and non-empty elements stay in the protocol.
   - `markup-validation.ts` checks the answer: same id set, same multiset of inline tags (name and attributes), balanced closing tags. A rejected batch is split and retried; valid segments from a partly wrong answer are kept. This also blocks injected attributes such as `javascript:` hrefs. Errors name the differing tag signatures (`inline tags or attributes were not preserved: missing <a id="nr4-11">; unexpected <b> ×2`, values cut at 40 characters, at most six listed), so a failed segment is diagnosable from the UI. `retranslateSegment` rejects with that reason alone; callers add their own context.
   - `retry-with-backoff.ts` retries 429, 5xx and network errors with exponential backoff and jitter (honors `Retry-After`, 5 attempts). Fatal errors (401, 403, 404) and five consecutive 4xx responses stop the run; other failures mark segments `error`.
   - `generate-guide.ts` drafts a book-specific guideline and glossary from a sample spread across the book. `estimate-cost.ts` estimates tokens for the remaining work (chars/4 for Latin, chars/1.5 for CJK) and USD from the prices in settings. `guideline-presets.ts` holds the `general`, `fiction`, `technical` and `psychology` starting guidelines.
   - `translate-sample.ts` picks passages for a sample translation (`selectSamplePassages`: usable chapters, i.e. not the table of contents and with enough text, are cut into equal groups in book order, one chapter is drawn per group with a seeded mulberry32 generator, and a contiguous run of segments of about 350 source words starts at a random position) and `translateSample` translates exactly those segments through `translateProject` over a view of pending copies, so batching, validation and retries are shared. Sampled segments are always translated again (that is how "translate samples again" works after a guideline edit), afterwards they are `translated` and a full run skips them. The selection is stored as the optional `Project.lastSample` (`{ seed, passages: [{ chapterHref, chapterTitle, segmentIds }] }`; project files without it still load); `estimateSampleCost` estimates just the sample.
   - `src/pricing/` implements `lookupModelPricing(model, { presetId, fetchImpl, signal, sources })`: it downloads the public OpenRouter `/models` list, then LiteLLM's `model_prices_and_context_window.json` (plain GETs with only an `Accept` header), converts per-token prices to USD per 1M, and matches by exact id, `<maker>/<model>` for the preset, normalized name (`.` `-` `_` `:` equivalent, lower case, maker prefix dropped) and finally a name without a trailing date stamp. Several differently priced candidates yield `undefined` instead of a guess. `withPricingCache` adds the 24h TTL cache (parsed rows only, stale data served when a refresh fails).
   - Glossary and guideline generation (`generateGuide`, `glossary/`) runs in three phases reported through `onProgress` (`extract`, `guideline`, `glossary`). `glossary/extract-candidates.ts` scans the whole book locally (no model call, linear time, about 0.5 s for 300k words): for space-separated scripts, capitalized multi-word runs with connectors ("Duke of York", "Mr. Darcy"), single capitalized words that recur mid-sentence more often than in lowercase, and frequent bigrams/trigrams without stopwords at either end (English static list; for other languages the 100 most frequent words); for CJK, frequent 2–4 character n-grams with apriori pruning; Thai, Lao, Khmer and Burmese yield no candidates. Each candidate carries its frequency and up to two snippets. `generate-guide-guideline.ts` asks for a guideline with fixed sections from ~18 passages (`generate-guide-passages.ts`) and appends it under `## Book-specific guideline` below the current (base) guideline; regenerating replaces only that block. `glossary/classify-candidates.ts` sends candidates in batches of 80 (concurrency from settings, `withRetry`, the first error cancels in-flight requests, an unparsable answer is retried once and then skipped); `glossary/merge-glossary.ts` keeps existing entries, dedupes case- and diacritics-insensitively, caps generated entries at `glossaryLimit = min(cap, max(30, ceil(sourceTokens / 650)))` (cap default 400, about one entry per 500 words) and sorts by type, then frequency. `GlossaryEntry.type` and `.count` are optional, so v3.0 project files still load.
   - Glossary in prompts: the translate and review system prompts carry no glossary, so they stay byte-identical across all batches of a run (Anthropic caches the marked system block; OpenAI, DeepSeek and Gemini cache identical prefixes automatically). `glossary/glossary-matcher.ts` selects the entries whose term occurs in the batch (case-insensitive, whole words for space-separated scripts, substring for CJK/Thai; a review batch also matches the term or translation in the draft) and they are sent in the user message as `"glossary":["term → translation (note)"]`.
5. **Export** (`export/export-epub.ts`). Rebuilds the EPUB from `sourceEpub`: removes segment markers, places translations per mode (`bilingual`, `bilingual-translation-first`, `translation-only`), sets `lang`/`xml:lang`, links a small stylesheet that fades the source text, and writes `mimetype` first and stored. Untranslated segments keep their source text. In bilingual modes the translated copy loses its `id` attributes (the source copy keeps the link targets), so restored page markers never duplicate ids; translation-only keeps them on the translation. EPUB 2 content documents are XHTML 1.1, so they are written without the HTML5 `<!DOCTYPE html>` (an explicit source doctype is kept), including documents rewritten by the sanitizer. Documents are serialized with the injected `XMLSerializer`, never with `innerHTML`, so the XHTML stays well formed. Translations go to the primary rendition; the other renditions of a multi-rendition book are kept and sanitized. Exports never carry active content, whether it comes from the model or the source book: `prune-package-files.ts` drops files no package document references (keeping `mimetype`, `META-INF/**`, every rootfile and `<link>` target in `container.xml` such as the rendition mapping document, and each rendition's manifest items and `<link>` targets) plus any XSLT. `strip-active-content.ts` then sanitizes every markup file, recognized by media type, by extension, or by content: any other kept file whose first non-whitespace character is `<`, whatever its declared type, except resources listed in `META-INF/encryption.xml` (obfuscated fonts) and files whose extension marks them as non-markup (CSS, scripts, images, fonts, audio, video, PDF, plain text, JSON; `markup-file-kind.ts`). Unknown extensions are checked. It removes scripts, `on*` attributes, `javascript:`-style URLs, `<template>`, frames, embeds, and `<object>` (unwrapped to its fallback content), and replaces markup that fails to parse with a safe stand-in. In every document it rewrites, comments and processing instructions inside the document element are removed and CDATA sections become escaped text. XHTML files, files recognized by content only (which a server may send without a media type), and files that lost active content are always rewritten; other XML and SVG files with nothing to remove are kept byte for byte, since they are served as XML. A file with any `xml-stylesheet` instruction is rewritten, keeping only instructions whose parsed `type` is exactly `text/css` (`xml-prolog.ts`). The in-app preview calls `exportEpub(project, mode, env, { preview: true })` (`preview-markers.ts`): segment blocks keep `data-et-id` and failed or untranslated ones get the classes `et-error` / `et-pending`; everything else is the same export. The default (no options) output is unchanged and never carries these markers (`test/export-preview-option.test.ts`).

## Environment injection

Core never touches DOM globals. Callers pass `DomEnv = { DOMParser, XMLSerializer }`: the browser natives in the web app, `linkedom` in the CLI and tests (`apps/cli/src/dom-env.ts` adds a small `XMLSerializer` shim because linkedom nodes serialize themselves). HTTP goes through `fetch`, injectable in `createProvider`.

## Providers (`providers/`)

`ChatProvider` has `listModels` and `chat`. One OpenAI-compatible adapter (Chat Completions over `fetch`) serves OpenAI, Gemini, OpenRouter, DeepSeek and custom URLs; Anthropic uses a native Messages adapter (header `anthropic-dangerous-direct-browser-access: true` for browser CORS, plus prompt caching). Models come from `GET {baseURL}/models` (Anthropic: `/v1/models`). The API key is attached only to requests for the configured base URL.

## Web app (`apps/web`)

Vite, React 19, Tailwind v4, Dexie (IndexedDB) and vite-plugin-pwa; UI strings in a small typed dictionary (Vietnamese and English). Books, settings and segment state are persisted in IndexedDB as translation proceeds, so a reload resumes. Features: multi-book library, side-by-side reader and editor with per-segment re-translation, glossary and guideline editor, cost estimate, export in the three modes, import and export of `.epubtrans` files. The Preview tab (`src/preview/`) renders that preview build with the vendored foliate-js reader (MIT, `src/preview/third-party/foliate-js/`) on emulated devices; reader settings are preview-only (`localStorage`), and a click on a paragraph opens the segment in the editor. Deployed as static files to GitHub Pages under `/epubtrans/`. See `apps/web` for the current structure.

Several tabs on one book: a translation job or sample run holds the Web Lock `epubtrans:job:<projectId>` for its whole run, so other tabs cannot start either and lock Edit/Retranslate; the job saves each segment with compare-and-set inside a Dexie transaction (an edit saved from another tab wins), and segment changes are announced on the BroadcastChannel `epubtrans:<projectId>` so open tabs refresh. Details: `apps/web/README.md`.

## CLI (`apps/cli`)

`src/run.ts` dispatches `translate`, `resume`, `export`, `models` and `presets` (`src/commands/`). Shared steps live in `src/pipeline.ts`: persist the project, look up missing prices in the public catalogs (`price-lookup.ts`, skipped by `--no-price-lookup`, never saved to the project file), print the estimate and ask for confirmation (Ctrl-C at the prompt exits with 130, see `prompt.ts`), then optionally generate the guide, run `translateProject` with throttled atomic saves of the project file (`project-store.ts`), flush on Ctrl-C or error, export the EPUB. API keys come only from `--api-key-file`, `EPUBTRANS_API_KEY` or the provider's own variable (`api-key.ts`); a key flag on argv is rejected. `EPUBTRANS_API_KEY` is skipped when a provider other than the default (`DEFAULT_PROVIDER_ID` in `settings.ts`, currently `openai`) comes only from the project file (no `--provider` or `--base-url` on that run), so a shared file cannot pick who receives the generic key; the CLI then fails with instructions. The default provider is exempt because a fresh import already sends the generic key there, which keeps "run the same command again" and `resume` working. `bun build --compile` produces single binaries (`scripts/build-cli.ts`).

## Security and privacy model

- No server and no telemetry: books and keys stay on the user's device.
- The key is sent only to the selected provider endpoint (Playwright network-log test covers the web app; the CLI builds the provider from the same core code).
- Model output is untrusted: it is validated against the source markup before it is stored or exported.
- Project files contain no key. Project JSON and IndexedDB rows are validated before use.
- Web: the key is memory-only unless the user ticks "remember key", which writes it to `localStorage` on the Pages origin `namnhfreelancer.github.io`. That origin is shared with the owner's other GitHub Pages sites, so any script served there could read it; documented in the README privacy section. Serving the app from a dedicated origin (for example a custom subdomain) would remove the sharing.
- CLI: the provider endpoint is never read from a project file (shared files could otherwise redirect the key). Presets use their own endpoint unless `--base-url` is passed on that run; `custom` requires `--base-url` on every run. Every request to the provider, including the `--generate-guide` call, happens only after the cost confirmation. The public price lookup may run before it because it is a keyless GET to `openrouter.ai` and `raw.githubusercontent.com`.
- Web preview: foliate-js renders each section as a blob: document in an iframe, which inherits the app CSP. The policy adds `frame-src blob:`, `style-src 'unsafe-inline' blob:` and `font-src blob:` for that; `script-src` stays `'self'`. Book scripts cannot run: exports are stripped of active content, foliate is told to skip script resources, and each section document gets its own `script-src 'none'` policy (the iframe keeps foliate's `allow-scripts` sandbox flag, which it needs for event listeners in WebKit). Preview settings never reach an export.
- Price catalogs: the web app and CLI query them with bare GETs (no `Authorization`, no body); the Playwright key-leak test intercepts both hosts with fixtures and asserts they never receive the key. The web CSP already allows `https:` in `connect-src`, so no change was needed.

## Release flow

Conventional commits on `main` drive release-please. Merging the release PR creates a tag and GitHub Release; the same workflow compiles the CLI binaries and uploads them with `SHA256SUMS`. Details in [deployment-guide.md](deployment-guide.md).
