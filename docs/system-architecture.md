# System architecture

epubtrans is a Bun-workspaces TypeScript monorepo. One engine (`@epubtrans/core`) is shared by a browser app and a CLI. There is no backend.

```
            +--------------------+       +------------------+
            |  apps/web          |       |  apps/cli        |
            |  React, IndexedDB  |       |  Bun binary      |
            |  DOM: browser      |       |  DOM: linkedom   |
            +---------+----------+       +---------+--------+
                      |      DomEnv, fetch, storage    |
                      +--------------+-----------------+
                                     v
                          +----------------------+
                          |  packages/core       |
                          |  import, segment,    |
                          |  translate, export,  |
                          |  project file        |
                          +----------+-----------+
                                     | HTTPS, key only to the chosen endpoint
                                     v
              Anthropic | OpenAI | Gemini | OpenRouter | DeepSeek | custom
```

## Core pipeline (`packages/core`)

1. **Import** (`import/import-book.ts`). `formats/detect-format.ts` recognizes EPUB, MOBI, AZW3 and FB2 from the bytes and file name, and TXT/Markdown by extension (`.txt`, `.md`, `.markdown`; binary content is refused). MOBI/AZW3 are converted by the vendored foliate-js parser (`third-party/foliate-js/mobi.js`, with an injected DOM), FB2 by an own converter, plain text by `plain-text-to-epub.ts` (headings in `plain-text-headings.ts`) and Markdown by `markdown-to-epub.ts` (`markdown-blocks.ts`, `markdown-front-matter.ts`, `markdown-inline.ts`, `markdown-inline-split.ts`; shared plumbing in `text-book.ts`). Text files are decoded as UTF-16 with a BOM, else UTF-8, else Windows-1252. TXT chapters start at explicit chapter lines ("Chapter 3", "CHAPTER IV.", "Part One", "Prologue", a bare upper-case roman numeral or number, `第三章`) when there are at least two, else at short lines set off by two blank lines, else the text is cut into chunks of 40 paragraphs; wrapped prose lines are joined, short verse lines keep `<br/>`. A chapter line must read like a title (roman numerals in upper case, a capitalized title after the number, no clause-ending punctuation) and must not be followed by a line starting in lower case; bare numbers also need a complete sentence before them and count only when most of them qualify (page numbers of scanned books fall mid-sentence). Markdown follows book-friendly rules rather than strict CommonMark: a file without any blank line (outside fenced code) has one paragraph per line, as in TXT, where setext underlines still make headings; a leading `---` block is front matter only when every line in it is YAML (`key: value` with an identifier key in any case such as `Cover-Image`, list items or indented lines under a key), at least one key is a well-known metadata key (`title`, `author`, `lang`, `date`, …) and no key is all caps (script speakers such as `HAMLET:`), otherwise it is a scene break; empty headings start no chapter; quotes nest at most 8 deep; inline parsing is one linear pass with a delimiter stack (unmatched delimiters stay text), linear in newlines too, so a huge hard-wrapped paragraph imports in well under a second per MB. Chapters start at level-1 headings when there are two or more, else at level-2 headings; title from front matter (quoted values unescaped), the only level-1 heading or the file name. In both formats a paragraph longer than about 2000 tokens is split at sentence ends (`split-long-text.ts`), so every segment fits one model answer; Markdown is split after inline rendering (`markdown-inline-split.ts`), closing and reopening emphasis and links at a cut. Every element is built through the DOM; raw HTML is never passed through (tags dropped, script-like content removed) and links keep a target only for http(s)/mailto. Everything is normalized into one in-memory EPUB package, so the later stages have a single path. DRM is detected and rejected with an error naming the scheme: MOBI encryption flag, `META-INF/license.lcpl` (Readium LCP), `META-INF/sinf.xml` (Apple FairPlay), `META-INF/rights.xml` (Adobe ADEPT) or a non-font `encryption.xml`.
2. **Segmentation** (`segment/segment-document.ts`). Block-level text in each content document is split into segments with ids `c{chapter}-{n}`; segment markers (`data-et-id`) are written into the normalized EPUB. Code, `pre`, math, SVG and similar blocks are skipped. The table of contents becomes chapter 0 (`TOC_CHAPTER_TITLE`) so TOC titles are translated too.
3. **Project** (`types.ts`). A `Project` holds settings, chapters with segments (`pending`, `translated`, `reviewed`, `error`, plus the optional non-blocking `warning: 'identical'`) and the normalized `sourceEpub` bytes. Optional settings added later (`maxSegmentsPerBatch`, `identicalMinLetters`, `cachedInputRatio`, `reasoning`) are validated when present; unknown future values of `reasoning` and `warning` are dropped instead of rejecting the file. `project/project-file.ts` saves it as a `.epubtrans` zip (`project.json` + `source.epub`) and validates untrusted state on load (`validateProjectState`, also used for IndexedDB rows).
4. **Translation** (`translate/`).
   - `translate-project.ts` translates every `pending` or `error` segment (that is what makes runs resumable), in batches of up to about 1500 source tokens and at most `maxSegmentsPerBatch` segments (default 32, 1 to 200; short lines such as a table of contents would otherwise put 100+ segments into one request, where models start to drop or shift answers), with a configurable number of parallel requests (1 to 16). The estimate and samples use the same batching. With `twoPass`, a review pass follows over every `translated` segment. Segments with `userEdited: true` (the user wrote the translation by hand; optional in project files) are skipped by both passes, by samples and by the estimate unless the caller passes `overwriteUserEdited`; a successful `retranslateSegment` (an explicit user request) clears the flag.
   - Protocol (`prompt-protocol.ts`): system prompt = stable prefix (role, language pair, guideline) plus rules; the batch-relevant glossary travels in the user message (see below); user message = JSON `{"segments":[{"id","html"}]}`; the model must answer the same JSON shape.
   - `empty-element-markers.ts` keeps empty inline elements away from the model. Page markers such as `<a id="p49"></a>` or `<span epub:type="pagebreak" id="p12"></span>` hold no text, so a model restructuring the sentence drops them and the segment would fail validation every time. Before a batch is sent (translate pass, review pass for both source and draft, `retranslateSegment`, samples), every non-void element without text or void elements inside (a marker, or a wrapper holding only markers such as `<span><a id="x"></a></span>`, but never an element nested in one of the same name) is detached together with the share of source text characters before it. After the reduced answer validates, the elements are put back at the same text fraction, snapped to the nearest word start (any character for CJK/Thai-like text without spaces), never inside a tag or inside an element of the same name, in original order, with 0 and 1 meaning start and end. A review reuses the draft's marker positions when the draft carries the same markers. The restored HTML is validated again against the full source, so stored translations keep the ids that TOC and index links point to. Void elements (`br`, `img`) and non-empty elements stay in the protocol.
   - `markup-validation.ts` checks the answer: same id set, same multiset of inline tags (name and attributes), balanced closing tags. A rejected batch is split and retried; valid segments from a partly wrong answer are kept. This also blocks injected attributes such as `javascript:` hrefs. Errors name the differing tag signatures (`inline tags or attributes were not preserved: missing <a id="nr4-11">; unexpected <b> ×2`, values cut at 40 characters, at most six listed), so a failed segment is diagnosable from the UI. `retranslateSegment` rejects with that reason alone; callers add their own context.
   - `retry-with-backoff.ts` retries 429, 5xx and network errors with exponential backoff and jitter (honors `Retry-After`, 5 attempts). Fatal errors (401, 403, 404) and five consecutive 4xx responses stop the run; other failures mark segments `error`.
   - `identical-translation.ts`: after a translation validates, `isIdenticalTranslation` compares source and translation text (tags, entities, URLs, e-mail addresses, case and punctuation ignored) and sets `warning: 'identical'` when they match, unless the source and target language are the same, the text has fewer than `identicalMinLetters` letters (default 12, 0 turns the check off), or every word starts with a capital (names, titles). The flag never blocks or retries anything; export uses the translation. A hand edit in the web app clears it.
   - Usage: providers report cached input tokens (`TokenUsage.cachedInput`: OpenAI-compatible `prompt_tokens_details.cached_tokens`, DeepSeek `prompt_cache_hit_tokens`, Anthropic `cache_read_input_tokens`; `cacheWriteInput`: Anthropic `cache_creation_input_tokens`), both included in `input`. `usage-cost.ts` prices them with `cachedInputRatio` from the settings, else the preset's documented ratio, else 1.
   - `generate-guide.ts` drafts a book-specific guideline and glossary from a sample spread across the book. `estimate-cost.ts` estimates tokens for the remaining work (chars/4 for Latin, chars/1.5 for CJK) and USD from the prices in settings. It sums per-segment facts instead of building every request: source sizes and each segment's glossary hits are cached per segment (hits per glossary array), and a batch's glossary is the union of its segments' hits (the review pass reuses the source hits instead of scanning drafts). The result matches the per-batch filter within a fraction of a percent; with a 400-entry glossary, a recompute after a finished segment takes 2 ms (400 pages) to 6 ms (2000 pages) and after a glossary edit 15 to 25 ms (400 pages) or 40 to 50 ms (2000 pages) in Node and Bun; the first estimate of a session also tokenizes the book (about 0.1 s for 400 pages, 0.35 s for 2000). `guideline-presets.ts` holds the `general`, `fiction`, `technical` and `psychology` starting guidelines.
   - `translate-sample.ts` picks passages for a sample translation (`selectSamplePassages`: usable chapters, i.e. not the table of contents, not back matter recognized by title (index, notes, bibliography, acknowledgments, copyright, in a few languages) and with enough text, are cut into equal groups in book order, one chapter is drawn per group with a seeded mulberry32 generator, and a contiguous run of segments of about 350 source words starts at a random position) and `translateSample` translates exactly those segments through `translateProject` over a view of pending copies, so batching, validation and retries are shared. Sampled segments are always translated again (that is how "translate samples again" works after a guideline edit), afterwards they are `translated` and a full run skips them. `translateSample` returns `{ selection, failed, keptEdited }`: hand-edited segments are skipped (`keptEdited`), and a failed sample translation never downgrades a segment that already had a translation (it keeps translation and status and is only listed in `failed`). The selection is stored as the optional `Project.lastSample` (`{ seed, passages: [{ chapterHref, chapterTitle, segmentIds }] }`; project files without it still load); `estimateSampleCost` estimates just the sample.
   - `src/pricing/` implements `lookupModelPricing(model, { presetId, fetchImpl, signal, sources })`: it downloads the public OpenRouter `/models` list, then LiteLLM's `model_prices_and_context_window.json` (plain GETs with only an `Accept` header), converts per-token prices to USD per 1M, and matches by exact id, `<maker>/<model>` for the preset, normalized name (`.` `-` `_` `:` equivalent, lower case, maker prefix dropped) and finally a name without a trailing date stamp. The fuzzy rules only consider plain ids (segments of letters, digits and `._~:@+-`), so a tampered catalog row cannot win with an odd prefix. Several differently priced candidates yield `undefined` instead of a guess. `withPricingCache` adds the 24h TTL cache (parsed rows only, stale data served when a refresh fails).
   - Glossary and guideline generation (`generateGuide`, `glossary/`) runs in three phases reported through `onProgress` (`extract`, `guideline`, `glossary`). `glossary/extract-candidates.ts` scans the whole book locally (no model call, linear time, about 0.5 s for 300k words): for space-separated scripts, capitalized multi-word runs with connectors ("Duke of York", "Mr. Darcy"), single capitalized words that recur mid-sentence more often than in lowercase, and frequent bigrams/trigrams without stopwords at either end (English static list; for other languages the 100 most frequent words); for CJK, frequent 2–4 character n-grams with apriori pruning; Thai, Lao, Khmer and Burmese yield no candidates. Each candidate carries its frequency and up to two snippets. `generate-guide-guideline.ts` asks for a guideline with fixed sections from ~18 passages (`generate-guide-passages.ts`) and appends it under `## Book-specific guideline` below the current (base) guideline, wrapped in `<!-- epubtrans:generated:start -->` / `<!-- epubtrans:generated:end -->` marker lines (the model's free-form fallback text may contain any headings, so only the end marker reliably ends the block); regenerating replaces only that block. A guideline from an older version without the end marker keeps the previous rule: the block ends at the next level-1/2 heading, so a section the user added below it under its own heading is kept. `glossary/classify-candidates.ts` sends candidates in batches of 80 (concurrency from settings, `withRetry`; a fatal error or abort cancels in-flight requests, while a batch whose request still fails after the retries, or whose answer stays unparsable after a second request, is skipped so finished batches are kept; only when every batch fails does generation fail); `glossary/merge-glossary.ts` keeps existing entries, dedupes case- and diacritics-insensitively, caps generated entries at `glossaryLimit = min(cap, max(30, ceil(sourceTokens / 650)))` (cap default 400, about one entry per 500 words) and sorts by type, then frequency. `GlossaryEntry.type` and `.count` are optional, so v3.0 project files still load.
   - Glossary in prompts: the translate and review system prompts carry no glossary, so they stay byte-identical across all batches of a run (Anthropic caches the marked system block; OpenAI, DeepSeek and Gemini cache identical prefixes automatically). `glossary/glossary-matcher.ts` selects the entries whose term occurs in the batch (case-insensitive, whole words for space-separated scripts with a short inflectional ending for Latin/Cyrillic/Greek words of 4+ letters, see the rule in the file; substring for CJK/Thai; a review batch also matches the term or translation in the draft). Texts are tokenized once into interned word ids (`word-vocabulary.ts`, a code-unit scanner in `word-scanner.ts` instead of Unicode regexes, which are slow in JavaScriptCore), and each distinct word is resolved once per glossary through a trie of first-word stems and they are sent in the user message as `"glossary":["term → translation (note)"]`.
5. **Word Wise hints** (`word-hints/`, export in `export/word-hint-markup.ts`). Short glosses over difficult words of the original text, generated by a separate run, never during translation.
   - Frequency data: `packages/core/data/wordfreq/<lang>.txt`, rank lists derived from wordfreq (CC BY-SA 4.0) by `scripts/generate-word-frequency-lists.ts` (committed, not run in CI): English 100k words, 13 more languages 30k each, about 4.7 MB. Core only parses them (`parseFrequencyList`); the web app imports them with `import.meta.glob(..., { query: '?url' })`, so Vite emits each as a static asset fetched on demand from the same origin (no CSP change); the CLI imports them `with { type: 'file' }`, which `bun build --compile` embeds in the binary. `wordHintLanguage` maps a source tag to a list (`zh-Hant`/`zh-TW` and unlisted languages: unsupported).
   - Selection (`select-hint-candidates.ts`, local, linear): the eligible text of each segment is read from `sourceHtml` without a DOM (`hint-text.ts`: text between tags, skipping code, pre, math, svg, ruby, sub/sup, note references, link text (`a[href]`), form controls and labels, noscript and embedded-content fallback; `<br>`, block tags and skipped elements are boundaries), tokenized per text chunk with `Intl.Segmenter` (dictionary-based for zh/ja), and each occurrence is stored as (segment id, exact word, nth occurrence of that word in the segment). A token touching a letter of the neighbouring text without a boundary (drop caps such as `<span>A</span>lthough`, split emphasis; not in unspaced scripts) is "glued" and skipped on both the selection and the export side. A word is a candidate when its rank (min of the form and its lemma; English: rule-based lemmatizer `english-lemmatizer.ts` with an irregular table, base forms validated against the list, unlisted words against the book's own words) is above the level threshold (levels 1–5 → ranks 25k/15k/9k/5k/2.5k, labelled about C2…A2), or when it is unlisted but lowercase in a cased script, or an unlisted Han word of 2+ characters (zh/ja lists are only 30k deep; unlisted single characters, kana and Korean eojeol never qualify). An unlisted Han word that splits into listed words (segmenter tokens such as 笑了, 我的) takes the rank of the rarest part of its best split (`han-unlisted-words.ts`), so it qualifies only at levels where that part would; a `zh` book whose text is Traditional (character sampling over 53 frequent Traditional/Simplified pairs) never counts unlisted Han words as rare. The lemmatizer prefers the plain `-s` reading and the silent-e reading unless another listed reading is far more frequent or the book writes one reading in lowercase and never uses the other (a word with several readings is kept through the scan while any reading could qualify, and settled from the words of the whole book afterwards), undoubles `-sses`/`-zzes` only when the doubled form is unlisted, and ignores corpus debris (`quot`, `amp`, `nbsp`…) and list entries that are only names (`moore`, `tampere`…). A qualifying lemma brings every occurrence of all its forms, each with its own form rank, also forms too common for the level, so stored entries cover the lemma at every level. Skipped: numbers, words under 3 letters (not CJK), corpus debris, glossary names, capitals in mid-sentence or after an opening bracket/colon following lowercase prose (not in German), capitals the book never writes in lowercase (twice or more, or once mid-sentence; listed words in the top 20k count as names only with a mid-sentence capital), capitals right after a quote opening that follows a comma or colon (`writes, “Universally`) unless the word is in the top 20k or written in lowercase elsewhere, the TOC and back-matter chapters (index, notes, bibliography…, same title detection as samples).
   - Glosses (`generate-word-hints.ts`, `gloss-protocol.ts`): items `{id, word, lemma, context}` (context = sentence with the word marked ⟦…⟧), 40 per request, concurrency from settings, `withRetry`, the first provider error cancels in-flight requests. Round 1 sends up to two contexts per lemma; if they agree on one sense label the gloss applies to every occurrence, otherwise round 2 sends up to 12 occurrences with the known senses (`senses:[{id,gloss}]`) so the model reuses a label; the remaining occurrences take the nearest decided sense. Glosses are cleaned (tags, controls, format characters except ZWNJ/ZWJ and XML-invalid characters stripped, wrapping quotes/brackets dropped while balanced inner ones stay, ≤5 words/40 chars); an unparsable answer is requested again once, unusable items are retried once, then the lemma counts as failed and is sent again next run. `skip: true` (names, non-words) is stored as an entry without senses and never resent. `planWordHints` decides per occurrence for the same language pair: new lemmas are sent whole, a glossed lemma whose entry lacks some occurrences is sent with only those and its known senses (straight to round 2; the result is merged into the entry), skipped lemmas are never resent; another source/gloss pair starts over. `estimateWordHintsCost` counts round 1 exactly and models round 2 (plus the known-sense lemmas). The web app reuses the scheduled plan on Generate while the project version and plan inputs are unchanged (`word-hints-plan-cache.ts`).
   - Storage: optional `ProjectSettings.wordHints` (enabled, level, glossLang, style `ruby|inline`, maxPerParagraph, perChapter) and `Project.wordHints` (`{sourceLang, glossLang, entries:[{lemma, rank, senses:[{id,gloss}], occurrences:[{segmentId, word, nth, sense, rank?}]}]}`, `rank` per occurrence being the form's rank, absent in older files where the entry rank applies); both validated in `validateProjectState` (occurrences must name a sense of their entry, settings are clamped); older files load unchanged.
   - Export: `planWordHintExport` filters each occurrence by its form rank against the level threshold, keeps the first `perChapter` occurrences per lemma sense and chapter, then the `maxPerParagraph` rarest per segment; `applyWordHints` finds each occurrence by re-counting words per text node in the exported DOM and inserts `<ruby class="et-ww">word<rp> (</rp><rt lang xml:lang>gloss</rt><rp>)</rp></ruby>` (paragraph class `et-ww-p` for line height) or `word<span class="et-ww-i"> (gloss)</span>`; glosses are text nodes only, and glosses and translations lose XML-invalid characters (`util/xml-chars.ts`) before export, translations also after HTML parsing (`convertHtmlNodes` strips text and attribute values, since the parser decodes `&#xFFFE;` or `&#1;` into raw characters). EPUB 2 packages always get the inline form (ruby is not in XHTML 1.1). Hints apply before the translation is placed, in `bilingual`, `bilingual-translation-first` and `original`, never in `translation-only` or the navigation document.
6. **Export** (`export/export-epub.ts`). Rebuilds the EPUB from `sourceEpub`: removes segment markers, places translations per mode (`bilingual`, `bilingual-translation-first`, `translation-only`; `original` keeps the source text only and lists only the source language), sets `lang`/`xml:lang`, links a small stylesheet that fades the source text, and writes `mimetype` first and stored. Untranslated segments keep their source text. In bilingual modes the translated copy loses its `id` attributes (the source copy keeps the link targets), so restored page markers never duplicate ids; translation-only keeps them on the translation. EPUB 2 content documents are XHTML 1.1, so they are written without the HTML5 `<!DOCTYPE html>` (an explicit source doctype is kept), including documents rewritten by the sanitizer. Documents are serialized with the injected `XMLSerializer`, never with `innerHTML`, so the XHTML stays well formed. Translations go to the primary rendition; the other renditions of a multi-rendition book are kept and sanitized. Exports never carry active content, whether it comes from the model or the source book: `prune-package-files.ts` drops files no package document references (keeping `mimetype`, `META-INF/**`, every rootfile and `<link>` target in `container.xml` such as the rendition mapping document, and each rendition's manifest items and `<link>` targets) plus any XSLT. `strip-active-content.ts` then sanitizes every markup file, recognized by media type, by extension, or by content: any other kept file whose first non-whitespace character is `<`, whatever its declared type, except resources listed in `META-INF/encryption.xml` (obfuscated fonts) and files whose extension marks them as non-markup (CSS, scripts, images, fonts, audio, video, PDF, plain text, JSON; `markup-file-kind.ts`). Unknown extensions are checked. It removes scripts, `on*` attributes, `javascript:`-style URLs, `<template>`, frames, embeds, and `<object>` (unwrapped to its fallback content), and replaces markup that fails to parse with a safe stand-in. In every document it rewrites, comments and processing instructions inside the document element are removed and CDATA sections become escaped text. XHTML files, files recognized by content only (which a server may send without a media type), and files that lost active content are always rewritten; other XML and SVG files with nothing to remove are kept byte for byte, since they are served as XML. A file with any `xml-stylesheet` instruction is rewritten, keeping only instructions whose parsed `type` is exactly `text/css` (`xml-prolog.ts`). The in-app preview calls `exportEpub(project, mode, env, { preview: true })` (`preview-markers.ts`): segment blocks keep `data-et-id` and failed or untranslated ones get the classes `et-error` / `et-pending`; everything else is the same export, Word Wise hints included. The default (no options) output is unchanged and never carries these markers (`test/export-preview-option.test.ts`).
   - **Export style** (`export-style/`): the optional per-book `settings.exportStyle` (source, translation, block spacing, hint look, or a preset from `export-style-presets.ts`) is validated strictly (`export-style-validation.ts`: unknown keys rejected, except in project files, template files and `--style-file`, where keys a newer version added are dropped and reported to the user; colors normalized to `#rrggbb`, numbers in range, fonts from an allowlist), again inside `exportEpub`, and turned into the generated `epubtrans.css` only (`export-style-css.ts`; never inline styles, never a background color, CSS 2.1 plus `opacity` and `@font-face` so EPUB 2 readers accept it). Without a style the stylesheet is byte-identical to the previous default. Translation-only exports mark translated blocks `et-tr` (and link the stylesheet) only when the style changes the translation. Style template files (`style-templates.ts`, `{"format": "epubtrans-style-templates", "version": 1, "templates": [...]}`, at most 64 KB and 100 templates) are shared by the web app's template import/export and the CLI's `--style-file`.
   - **Embedded fonts** (`export-style/embedded-fonts.ts`, files in `data/fonts/`): a style may pick Literata, Noto Serif, Be Vietnam Pro or Noto Sans (SIL OFL 1.1 TrueType subsets with Vietnamese coverage). The fonts the mode shows (source font in bilingual layouts, translation font except in `original`) are loaded through `ExportOptions.loadFontFile` (web: same-origin fetch; CLI: files embedded in the binary), checked (TrueType magic, plain-text license) and written to `epubtrans-fonts/` next to the stylesheet with their license file, as manifest items (`font/ttf` in EPUB 3, `application/x-font-truetype` in EPUB 2; licenses `text/plain`), never obfuscated (`embedded-font-package.ts`).
   - **Identifier** (`export-identifier.ts`): every rendition gets a new first `dc:identifier` `urn:uuid:<v5 of source id + target language + mode>` and `unique-identifier` points to it (also the NCX `dtb:uid`); the source identifiers stay, and the source id is added as `dc:source`. When `META-INF/encryption.xml` lists anything (font obfuscation, whose key derives from the identifier) the source identifier is kept. SHA-1 for the v5 UUID is a small pure implementation (`util/name-based-uuid.ts`), so it works outside secure contexts too.
   - **Attribution** (`attribution-page.ts`): with `settings.attribution === true` (default off), a translating mode and at least one translated segment, a colophon page "Translated with <model> by epubtrans" (target language when the phrase table has it, else English; the model name only as escaped text) is appended to the end of the spine. It is a new document, so no existing page changes (the least invasive valid choice, since title pages differ per book). In a pre-paginated (fixed-layout) EPUB 3 its spine entry carries `rendition:layout-reflowable`, so it needs no viewport. The page is marked (`id="epubtrans-attribution"` with class `et-attr`): importing an epubtrans export skips it, and exporting again replaces it; likewise an earlier `epubtrans-uid` identifier is reused and the new id is derived from the original book's identifier.

## Environment injection

Core never touches DOM globals. Callers pass `DomEnv = { DOMParser, XMLSerializer }`: the browser natives in the web app, `linkedom` in the CLI and tests (`apps/cli/src/dom-env.ts` adds a small `XMLSerializer` shim because linkedom nodes serialize themselves). HTTP goes through `fetch`, injectable in `createProvider`.

## Providers (`providers/`)

`ChatProvider` has `listModels` and `chat`. One OpenAI-compatible adapter (Chat Completions over `fetch`) serves OpenAI, Gemini, OpenRouter, DeepSeek and custom URLs; Anthropic uses a native Messages adapter (header `anthropic-dangerous-direct-browser-access: true` for browser CORS, plus prompt caching). `createProvider(..., { reasoning })` maps `low`/`off` to `reasoning_effort: low|none` (OpenRouter: `reasoning: { effort }`; when `none` is rejected, `off` tries `minimal` next) or Anthropic `thinking` (`disabled`, or `enabled` with the 1024-token minimum budget added to `max_tokens` and no custom temperature). `reasoning-fallback.ts` steps through the field variants on HTTP 400/422 (for `off`: `none`, `minimal`, then no field); the variant that succeeds is remembered for the endpoint, model and level for the session (page or process), and other statuses never trigger the fallback. The rejected attempt never reaches the batch runner, so it does not count toward the consecutive-4xx stop. Models come from `GET {baseURL}/models` (Anthropic: `/v1/models`). The API key is attached only to requests for the configured base URL.

## Web app (`apps/web`)

Vite, React 19, Tailwind v4, Dexie (IndexedDB) and vite-plugin-pwa; UI strings in a small typed dictionary (Vietnamese and English). Books, settings and segment state are persisted in IndexedDB as translation proceeds, so a reload resumes. Features: multi-book library, side-by-side reader and editor with per-segment re-translation (failed segments and identical-translation warnings each have their own count, navigation and filter), glossary and guideline editor with CSV/TSV/JSON glossary import (merge or replace, `glossary/glossary-file.ts`) and CSV/JSON export, cost estimate (cached input price configurable), reasoning setting per provider, Word Wise hints (setup card with level, gloss language, estimate and "Generate hints"; style and density on the export tab), export in the four modes, import and export of `.epubtrans` files. Changing the target language of a book with translations opens a dialog (keep them, or reset every segment to pending); the reset (`updateSettingsAndResetTranslations`) runs under the book's cross-tab job lock, writes settings and segment rows in one IndexedDB transaction and bumps the book's settings revision, so a retranslation still in flight in any tab cannot store its old-language result. Hints are stored in the IndexedDB table `hints` (schema version 2, one row per lemma, written as each finishes with compare-and-set against the run's language pair, so a run whose hints were replaced meanwhile stops instead of mixing pairs; the project row keeps the language pair as `hintLanguages`); a hints run is a job like translation and samples (same Web Lock, refused while another job of the book runs in the tab, and it blocks Start, samples and the reader's Retry all failed in turn); its candidate plan and estimate are scheduled like the book estimate (debounced, when idle, kept during runs); it announces `hints` on the BroadcastChannel when it ends so other tabs reload them. The footer credits wordfreq (CC BY-SA 4.0). The Preview tab (`src/preview/`) renders that preview build with the vendored foliate-js reader (MIT, `src/preview/third-party/foliate-js/`) on emulated devices; reader settings are preview-only (`localStorage`), and a click on a paragraph opens the segment in the editor. The book style editor (`src/components/export-style/`) sits on the Export tab and next to the preview; each change is validated and saved to the book's settings, which rebuilds the preview (debounced). Embedded fonts are fetched lazily from the app's own origin (`src/lib/embedded-font-files.ts`; not precached, never inlined as data: URLs); the service worker caches a font file on first use (cache first, cache `epubtrans-fonts-v1`, at most 24 entries; `pwa-font-caching.ts`), so it works offline afterwards. Style templates live in the IndexedDB table `styleTemplates` (schema version 3, names unique ignoring case, every row validated on read). WebMCP `export_epub` accepts an optional saved template name (this export only) and `update_book_settings` a style preset (replacing a custom style asks the user). Deployed as static files to GitHub Pages under `/epubtrans/`. See `apps/web` for the current structure.

WebMCP (`src/webmcp/`): when the browser offers `document.modelContext`, `useWebMcpTools` (mounted in the app shell) registers 14 static tools for in-browser AI agents (list of tools in the README). Every registration shares one AbortController, and no `exposedTo` is set, so the tools are same-origin only. `model-context-adapter.ts` is the only file that touches the API; it feature-detects it and is a no-op otherwise (no polyfill). Each handler re-validates its input against its JSON schema (`tool-input.ts`) and calls the same functions as the UI: `startTranslation` (`lib/start-translation.ts`, shared with `useStartTranslation`), the guide-generation store (`lib/guide-jobs.ts`, which the guideline card also renders), the sample, hints and translation job registries, and `resolveRunPrices`/`estimateRunCost` (`lib/run-pricing.ts`, shared with the cost card). Each tool always resolves a JSON string `{ok,...}` or `{ok:false,error,hint}` of at most 1,500 characters (`tool-result.ts`) and never rejects. Tools that change a book navigate to its tab so the user sees the change.

Several tabs on one book: a translation job, sample run or hints run holds the Web Lock `epubtrans:job:<projectId>` for its whole run, so other tabs cannot start either and lock Edit/Retranslate; the job saves each segment with compare-and-set inside a Dexie transaction (an edit saved from another tab wins), and segment and settings changes are announced on the BroadcastChannel `epubtrans:<projectId>` so open tabs refresh. Settings are saved as patches merged in a transaction (nested ones field by field), and every run, including a hints run, re-reads them from storage before sending. Details: `apps/web/README.md`.

## CLI (`apps/cli`)

`src/run.ts` dispatches `translate`, `resume`, `sample`, `hints`, `export`, `glossary`, `models` and `presets` (`src/commands/`). Every command prints through `terminalSafeIo` (`terminal-text.ts`), which strips escape sequences and control characters (except newline and tab) from all output, because book text, project files, model answers and price catalogs are untrusted; only the CLI's own progress redraw prefix is kept. `hints` opens or imports the project (`open-project.ts`, shared with `sample`; `--gloss-lang` stands in for `--to` on a new book), loads the embedded frequency list (`word-frequency.ts`), prints the hints estimate, asks for confirmation, generates with throttled saves and exits 3 when some words failed; `translate`, `resume` and `export` take `--word-wise` and the hint options (`hint-flags.ts`) and only apply existing hints; they (and `hints`) also take `--style-file` (a style or a one-template file, validated by core; `style-flags.ts`) and `translate`, `resume` and `export` take `--attribution` / `--no-attribution` (saved by `translate` and `resume`, this export only for `export`). Bundled fonts are imported `with { type: 'file' }` like the frequency lists (`embedded-font-files.ts`) and passed to core as the export's font loader. Shared steps live in `src/pipeline.ts`: persist the project, look up missing prices in the public catalogs (`price-lookup.ts`, 5 s timeout since it runs before the confirmation, skipped by `--no-price-lookup`, never saved to the project file), print the estimate and ask for confirmation (Ctrl-C at the prompt exits with 130, see `prompt.ts`), then optionally generate the guide, run `translateProject` with throttled atomic saves of the project file (`project-store.ts`), flush on Ctrl-C or error, export the EPUB. API keys come only from `--api-key-file`, `EPUBTRANS_API_KEY` or the provider's own variable (`api-key.ts`); a key flag on argv is rejected. `EPUBTRANS_API_KEY` is skipped when a provider other than the default (`DEFAULT_PROVIDER_ID` in `settings.ts`, currently `openai`) comes only from the project file (no `--provider` or `--base-url` on that run), so a shared file cannot pick who receives the generic key; the CLI then fails with instructions. The default provider is exempt because a fresh import already sends the generic key there, which keeps "run the same command again" and `resume` working. `glossary export` writes a project's glossary as CSV, TSV or JSON; `translate`/`sample`/`hints --glossary-file` merges one in (validated before any request, project entries win). Run tuning flags (`--max-segments`, `--reasoning`, `--cached-ratio`, `--identical-min-letters`) are stored in the project settings. The run summary lists translations identical to the source, and usage lines show cached tokens. `bun build --compile` produces single binaries (`scripts/build-cli.ts`).

## Security and privacy model

- No server and no telemetry: books and keys stay on the user's device.
- The key is sent only to the selected provider endpoint (Playwright network-log test covers the web app; the CLI builds the provider from the same core code).
- Model output is untrusted: it is validated against the source markup before it is stored or exported.
- Project files contain no key. Project JSON and IndexedDB rows are validated before use.
- Web: the key is memory-only unless the user ticks "remember key", which writes it to `localStorage` on the Pages origin `namnhfreelancer.github.io`. That origin is shared with the owner's other GitHub Pages sites, so any script served there could read it; documented in the README privacy section. Serving the app from a dedicated origin (for example a custom subdomain) would remove the sharing.
- CLI: the provider endpoint is never read from a project file (shared files could otherwise redirect the key). Presets use their own endpoint unless `--base-url` is passed on that run; `custom` requires `--base-url` on every run. Every request to the provider, including the `--generate-guide` call, happens only after the cost confirmation. The public price lookup may run before it because it is a keyless GET to `openrouter.ai` and `raw.githubusercontent.com`.
- Web preview: foliate-js renders each section as a blob: document in an iframe, which inherits the app CSP. The policy adds `frame-src blob:`, `style-src 'unsafe-inline' blob:` and `font-src blob:` for that; `script-src` stays `'self'`. Book scripts cannot run: exports are stripped of active content, foliate is told to skip script resources, and each section document gets its own `script-src 'none'` policy (the iframe keeps foliate's `allow-scripts` sandbox flag, which it needs for event listeners in WebKit). The preview's copy of each section also drops `<meta http-equiv="refresh">` and prefetch/preconnect/dns-prefetch/prerender/preload/modulepreload `<link>` elements (`preview-network-hints.ts`), and external links open only for http(s)/mailto, in a new tab with `noopener,noreferrer` (`preview-external-link.ts`; the vendored `view.js` fallback does the same). Preview settings never reach an export.
- WebMCP tools never take or return an API key. `configure_provider` reports only `keyPresent`, and the custom base URL is not settable, so a stored key cannot be redirected. As a second line of defence, every output is scrubbed of the stored keys (provider text is redacted before it is clipped, so a cut cannot leave a key prefix), and a unit test plants a sentinel key and checks every tool's output for it.
- WebMCP spending and deletion need the user: `start_translation` and `delete_book` show a `window.confirm` (provider, model, remaining segments and estimate, or the title), and so does `import_book_from_url` (the host). A declined or suppressed dialog spends and deletes nothing. `start_translation` starts with the provider snapshot the user confirmed and refuses when the provider, base URL, model, key, two-pass mode or remaining work changed meanwhile. Book-derived text in dialogs is flattened (`dialogText`: no control, line-break or bidi characters). `retranslate_segment` refuses hand-edited segments, and `update_book_settings` does not apply a guideline preset while guide generation runs and refuses a target-language change on a book with translations unless `resetTranslations: true` is passed and the user accepts a `window.confirm` (refused too while a run holds the job lock). `configure_provider` may set the reasoning level (no key involved). Deleting a book (library page or `delete_book`, via `lib/delete-book-from-device.ts`) cancels its guide generation and sample before removing it. The paid tools that run without a dialog (guide, sample, single-segment retranslation) refuse while the book's job lock is held in this tab or another one.
- WebMCP outputs carrying book text, model output or provider errors are annotated `untrustedContentHint` and returned as clipped plain text in named fields. `import_book_from_url` accepts `https:` only (no local-service probing), sends no credentials and enforces the 300 MB cap while streaming; a redirect to a host other than the approved one is refused. Tools are same-origin only. Other GitHub Pages repos of the owner share the origin and could call them, but they can already read IndexedDB and `localStorage` directly. A dialog accepted by an agent that drives the browser over CDP cannot be told apart from the user's click (residual risk).
- Price catalogs: the web app and CLI query them with bare GETs (no `Authorization`, no body); the Playwright key-leak test intercepts both hosts with fixtures and asserts they never receive the key. The web CSP already allows `https:` in `connect-src`, so no change was needed.

## Release flow

Conventional commits on `main` drive release-please. Merging the release PR creates a tag and GitHub Release; the same workflow compiles the CLI binaries and uploads them with `SHA256SUMS`. Details in [deployment-guide.md](deployment-guide.md).
